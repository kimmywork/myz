Wrote an E2EE security hardening plan after re-verifying the audit against the code. Reviewed each finding: confirmed T1/T2/T4/T6/T7/T10/T14, corrected T3 (rotation does re-upload; the real gap is that old-keyId ciphertext is never purged), and upgraded T5 (missing sender checks let a compromised content script re-key the account to an attacker-known secret, which is a confidentiality escalation, not just DoS). The plan adds device binding (A becomes address/auth only; random data key wrapped to device public keys), per-device manifest signatures, Argon2id/high-entropy hardening, anti-rollback, rotation cleanup, local credential encryption, message authorization, lock renewal, and integrity checks; it separates shippable quick wins from breaking key-model increments and records that the key model must be decided before freezing the sub-stream v1 format.

## 2026-09-28T16:00:00

Recorded four security-model decisions and updated the hardening plan: no A-only recovery (D is wrapped only to device keys, losing all devices is unrecoverable); no strict forward secrecy is required, only that A alone cannot derive D; no backward compatibility, so the new account/format version replaces and purges the old root directly; and a determination that write-access revocation is impossible with pure S3 and a single shared static credential (requires either a minimal identity service issuing per-device short-lived credentials or per-device credentials plus per-device write areas), left as the remaining open decision. Replaced the v1→v2 migration increments with a clean-break increment and documented the accepted risk that remote-only records are lost.
