# 0.7 对抗分析：从四类用户的「0.7 之后的一天」拆这个版本

> 对象：`docs/plan/release-0.7.md`（2026-11-10 用户拍板范围；13:00 后计划按评审修订过 §3.2 / §3.4 / §3.6，本文已同步）
> 立场：不为这份计划背书。逐条问「这个场景里它解决了什么、会不会带来新问题、不做会怎样、怎么证明我错了」。
> 读法：结论先行，往下是四类用户的走查和六个靶子。全文约十分钟。

---

## 结论先行

1. **整页快照应当从 0.7 移出**。修订后的计划给它补了存储预算和 LRU 淘汰（§3.4），这解决了「配额写满后静默失败」，却把另一个矛盾摆到明面上：**快照承诺的是「以后还能看到」，而 LRU 淘汰掉的正是「以后」**。它的价值又集中在计划明确排除的页面类型上（无限滚动），是唯一能让 0.7 从几周变成两个月的单项。建议先用一天量「打开原页的失败率」，用数据决定要不要做。
2. **6 秒撤销不能直接搬到批量删除**。现有实现是「延迟写 + 撤销」，而它在宿主销毁时是**清定时器不提交**——批量场景下这会变成「用户以为删了，其实没删」。这个 bug 比误删更难发现。先把四种边界情况的结果定死，再谈秒数。
3. **图片存为记录不是「窄改动」**，它是本版第二个动数据模型的东西。记录 schema 里没有附件字段，而且「附件本地-only + 记录同步 + 导出不带附件」三者组合起来，会让这条记录在换设备后只剩一个占位框。
4. **批量能力有一处不对称**：缓存区给了批量删除，却不给批量「存为记录」。而这正是用户原话里「从暂存区把某些截图保存下来」的动作——只能一张张点。
5. **四个大改挤在一个版本里**：全面视觉重构 + 删除语义 + 数据模型变更 + 新存储子系统。任何一件失控都拖垮其余，且无法局部回退。

## 一、四类用户走一遍「0.7 之后的一天」

### A. 重度用户（几千条记录，每天用）

早上打开 dashboard。设计修订后，列表从「每行一张卡片」变成 56 高的紧凑行，一屏能看十几条——**这是他今天能立刻感知到的唯一变化**，而且是好的。

他要找上个月划的一条。搜索、筛选、进查看器。这里 0.7 没有改。查看器仍然是「记录 + 原文 + 打开原页」。

下午他要清理一批旧记录，勾了 40 条，点删除。按计划：即时消失 + 6 秒撤销。他删完就切去别的 tab 了。
**风险点**：撤销窗口和延迟写绑定（见靶子 2）。如果他切走的方式导致宿主销毁，这 40 条可能根本没删；如果他只是关掉 dashboard，撤销窗口结束、写入发生——两种结果都对，但没有任何提示告诉他哪一种发生了。

他打开一个大 PDF。阅读页现在有两个动作：单条「从列表移除」（即时消失 + 6 秒撤销）和「清空历史」（确认、不提供撤销）。按修订后的 §3.2 两条轴（能不能重建、作用范围）分开处置，两者不再打架。剩下的风险只有一个：**「从列表移除」既不删文件、也不删高亮**，这个语义必须让用户一眼看懂，否则他以为删掉的是高亮，回头发现还在。

### B. 刚换设备的人

他在旧电脑上划了两千条，新电脑装好扩展，走同步配对（要手工传串，这轮不改）。数据过来了——高亮都在。

但他上个月存的 12 条「截图记录」在新电脑上全是占位：「图片在本机」。
**这是 0.7 最说不清的一个坑**：他确实看到了一堆记录，点进去却没有内容。更糟的是，如果他在这时导出备份，那 12 条记录会以「有文字没有图」的形态被导出——一个看起来完整、实际残缺的备份。

而且快照也是本地-only 的话，同样的故事会在快照上看第二遍。

### C. 偶尔划线的人（一周几次）

设计修订让他觉得「这个产品变精致了」——但他一条记录都没多。

删除语义统一对他没感觉。批量对他没感觉（他没有几百条）。素材页对他没感觉。

**这个版本对他唯一的意义是「看起来更可信了」。** 这不是坏事，但要说清：0.7 不制造任何「他会向朋友推荐」的理由。这不构成本版必须改的问题，但它解释了为什么版本号之后要紧跟一个真功能版本。

### D. 在 X / 知乎这种无限滚动站点采集的人

这是最矛盾的一类。他的内容**最容易消失、最容易改版、最需要存档**（转发链、删除的帖子、动态加载的评论）。

而计划写得很明确：无限滚动页面**不做整页快照**，只以 record 为锚向两侧扩展、连续 N 个元素没命中就停（§3.4 第 101 行）。

也就是说：**最需要快照的人，被规则明确排除在外**；能得到完整快照的，是博客和新闻这类本来就不太会消失的页面。

## 二、六个靶子

### 靶子 1：整页快照——最贵的一块，价值最集中，也最容易被证伪

**它解决什么**：原页消失、改版、登录墙之后，用户还能看到当时标的那段话和它周围的内容。

**会带来什么新问题**：

1. **淘汰机制和「存档」这个词相矛盾——这是修订后计划带来的最硬一条。** §3.4 现在给了总量上限、LRU 淘汰、淘汰前提示，解决了「配额写满静默失败」。但它没解决语义：快照存在的全部理由就是「以后还能看到」，而 LRU 会在一个用户不知情的时刻删掉最旧的快照。「淘汰前提示一次」对一个一周后才回看的人没有作用——他打开时看到的仍然是找不到。存储上限是工程上必须的，但它把「存档」降级成「有期限的缓存」。这一条要么在 UI 上直说（「本机存档，空间不足时最早的最先被清」），要么就得给快照一个用户可管理的位置（哪些留、哪些清）。否则它是一句隐性承诺违约。
2. **价值错配**。计划排除无限滚动页，而那正是内容最易失的地方。普通文章页 URL 稳定、重访可靠，「打开原页」就能看到高亮。
3. **它与查看器的本质区别，计划没有说清**。查看器现在给的是「这条记录 + 原文 + 打开原页」。快照只有在三种情况下才明显更好：原页 404、原页改版、原页要登录。这三种情况的占比是未知数，而 4–6 周的投资押在它身上。
4. **它引入一种新的失败模式：有存档，但标不上。** 锚点降级顺序是「范围 → 文本引用 → 未定位」，最后一级的字面意思是「你的高亮在这里找不到」。快照可能给出一个「页面在、但标不上」的状态——比打不开原页更让人困惑。（注意：这不是快照独有的问题，DOM 路径锚点在原页改版后一样会失效；但原页上还有文本引用可以救，快照上如果版本对不上就是双输。）
5. **按页面存 + 版本列表**，意味着老记录的高亮可能落在旧版快照上，默认展示最新版时就是第 4 条那个状态。这是数据模型层面的耦合，不是 UI 能补的。
6. **节奏与维护成本**。S4 独占一个切片，4–6 周；它还是本版唯一的新存储子系统，要额外养一套上限、淘汰、失败提示。它和前三个切片没有依赖，但它是唯一会让 0.7 从「几周」变成「两个月」的一项。

**不做会怎样**：原页消失时，用户失去当时的上下文——这是真实损失，不是伪需求。但它可以用更便宜的方式部分兜底：原页打不开时，展示「记录原文 + 已保存的选中文字 + 采集时间」，这在现有数据里就有。

**怎么证明我错了（成本一天）**：
给「打开原页」加一个失败计数（404 / 超时 / 登录墙三类），跑两周。判据：
- 失败率 **< 10%** → 快照不是 0.7 的问题，推 0.8。
- 失败率 **> 20%** → 我对，但需求成立，快照提前。
- 10–20% → 只对高失败域名做快照（白名单），成本降到 1/3。

**替代方案**：0.7 只做「记录详情里的原文摘录 + 采集时间 + 打开原页失败提示」，不做存储子系统。这样「原页变了」这个场景至少有话说。

### 靶子 2：删除统一 + 6 秒撤销——秒数是小问题，延迟写才是

**它解决什么**：同一个「删除」在 content 能撤、在 Inbox 是永久、在阅读页没有。这是真的不一致，必须改。

**会带来什么新问题**：

1. **延迟写语义在宿主销毁时不安全**。`pending-delete.ts` 的 dispose 是「清掉所有定时器，不提交」（`content/highlight/pending-delete.ts:138-143`）。今天它只服务 content 层，风险有限；一旦提成共享能力、接到 dashboard 的批量删除上，就是：「删了 40 条 → 切走 → 40 条还在，用户以为删了」。**这是反向 bug，比误删更难发现，因为没人会去核对「删掉的东西还在不在」。**
2. **6 秒是从哪来的**。它是内容层的经验值：单条、页面内、眼睛还在原处、提示就在旁边。批量删 50 条时，注意力在操作条和列表整体，而且删除后列表会重排——6 秒未必够，用户也未必找得到撤销按钮。
3. **撤销提示的落点在 dashboard 没有定**。现在 Inbox 的撤销是行内提示（`InboxPage.tsx:127-140`），不是浮层；列表一长、一滚，它就出了视口。而设计规范只写了 toast 一种落位。0.7 要同时改这两件事（删除语义 + 视觉重构），如果提示形态在重构中被顺手改掉，撤销就变成一个「说过但找不到」的承诺。
4. **批量删除没有「已选 N / 共 M」的量级提示**。几千条时「全选」是危险动作。

**不做会怎样**：用户继续在 Inbox 里遇到「删除后不可撤销」的确认框（`useInboxActions.ts:104`），在 content 里遇到可撤销——学习成本永远存在。这条应该做。

**判据（实现前必须先写出来的决定表）**：

| 边界情况 | 必须的结果 |
|---|---|
| 撤销窗口内关掉 dashboard | 删除发生（或明确提示「未删除」） |
| 撤销窗口内切路由 | 删除发生 |
| 撤销窗口内断网 / 写入失败 | 删除没发生 + 用户被告知，不能静默 |
| 批量删 40 条时关页面 | 40 条全部一致（要么都删要么都没删，不能部分） |

四条里任何一条做不到「用户知道发生了什么」，批量删除就应该改成「立即写 + 回收站」，而不是「延迟写 + 撤销」。回收站是新功能，成本更高——所以这是一次真实的取舍，不是实现细节。

**秒数**：允许先按 6 秒做，但把「批量场景的撤销点击延迟」记成可测量（跑 5 个真实批量删除，量从点击到点撤销的间隔）。这是唯一能让秒数有依据的办法。

### 靶子 3：批量做窄——「窄」是按数据量定的，代价落在两个地方

**它解决什么**：文库有几百上千条，只能一条条点，是效率问题。选三个面（文库 / 缓存区 / 阅读页清空）是对的。

**会带来什么新问题**：

1. **缓存区的能力不对称**。批量删除有，批量「存为记录」没有（§3.6 明确不做）。而用户原话要的正是「从暂存区把某些截图也保存下来」。他一次截十张，要逐张点十次——而「落库」比「删除」风险更低（本地写入，不涉及数据丢失），没有理由比删除更严格。
2. **「全选」的语义没写**。全选是当前页，还是全部筛选结果？几千条时这两者差别巨大。至少要显示「已选 N（共 M）」，并让全选只作用于当前页。
3. **阅读页只给清空历史**，牺牲了「删掉某一本」。判据是「条目量级小」，但对用了几年的用户，阅读历史可能也有几百条。这一条我认可当前取舍（清空是唯一有确认的批量动作），但要写进「已知不做」，别让用户以为「阅读页没有删除」是永远如此。

**不做会怎样**：用户继续一条条点。这条应该做，但要补上「批量存为记录」，否则素材页的主要用途（挑选保存）会被交互卡死。

### 靶子 4：图片 / 视频存为记录——它其实在动数据模型，而且会造出「半边记录」

**它解决什么**：截图现在只进本地缓存区 + 下载到磁盘，dashboard 里看不到，也不进记录。用户「存了图找不到」。

**先纠正一个事实**：
- 缓存项本身**已经在磁盘上有一份**（`content/capture-media.ts:11`、`:136-140`，每次采集都 `downloadImage`）。所以「找不到」有一部分是文件系统能解决的，素材页补的是「在应用内浏览与挑选」。
- 计划写的「`kind = clip` + 附件引用」——但记录 schema 里**没有任何附件字段**（`packages/shared/src/schemas/records/v1.ts:13-38` 的全部字段：id / kind / sourceType / locator / text / html / contentType / note / tags / color / style / 时间 / sourceUrl / title / hostname / range / url / unreachable）。`RECORD_KINDS` 只有 highlight / clip / bookmark。
- 也就是说：**这不是窄改动，是新增记录字段 + 同步协议变更**，是 0.7 里第二件动数据模型的事（第一件是快照）。而 0.7 的前提之一恰恰是「同步是试验性功能」。

**会带来什么新问题**：

1. **半边记录**。附件本地-only、记录参与同步。换设备后：记录在、内容不在，占一个「图片在本机」的占位。用户感知不是「附件没同步」，是「我存的东西丢了」。
2. **导出：计划已经要求列出缺失清单——这是诚实，但不是完整。** §3.6 现在要求「导出结果写明 N 个附件未包含并给出清单」，「看起来完整、实际残缺」这一半被解决了。但清单不能替代恢复：用户拿走的备份仍然换不回那 12 张图，换设备后照样是空框。所以这条从「欺骗」降级为「已知缺口」，代价是发布说明必须把它说清，而不是埋在文档里。
3. **context 会不会被用**，目前只是假设。计划给图片默认带「来源页 + 标题 + 文字上下文 + 时间戳」，这是合理的默认，但没人证明用户会回看。

**两条路，必须选一条**：

- **A（推荐）**：0.7 不做「存为记录」。素材页只做浏览、删除、批量删除。用户要「带走」就下载（已经在下载）。这样 0.7 完全不碰数据模型，风险最小。
- **B**：做，但承认它是 schema 变更，并连带定义：附件是否同步（建议**同步**，否则就是半边记录）、导出是否带附件、换设备后如何呈现。这会把 0.7 再撑大一块。

**判据**：如果选 B，先回答一句——「这条记录的主要内容是那张图吗？」如果是，附件不同步就是错的；如果不是（图是附注），那这条记录的主体是文字上下文，附件不同步可以接受，但要在卡片上明确「图仅在本机」。

**怎么证明我错了**：A 方案上线后两周，看有多少条「素材 → 存为记录」被真正**再次打开**（不是存的时候点一下，是后来回看）。低于 10% 说明这个动作是收藏癖，不是需求，context 的编辑 UI 也不值得做。

### 靶子 5：工作区三栏——密度和「hover 才出现」是两个不同的赌注

**它解决什么**：现在一行 140–160px，一屏 5 行；用户是来扫视和处理的，留白让他多滚三屏。核心诊断是对的。

**会带来什么新问题**：

1. **「hover 才出现动作」把可发现性换成了密度**。删除、保留、标记这些动作平时藏着。对不熟电脑的人（用户的父母、同事），hover 不是一个他们会尝试的动作——**删不掉和找不到撤销是同一个问题的两面**。触屏常驻是对的，但笔记本触控板用户仍然算 hover 用户。
2. **Inbox 右栏放详情，与参考的骨架不是同一个东西**。Gmail 的读信是**替换主区**；右栏详情是「列表不消失 + 详情挤进来」。在 1440 下主区只剩 872，在 1280 下 712，一个带上下文的划线可能只能显示三行。处理队列时视线要在左右两栏之间跳。这是「缝合两种参考」的代价，计划没有正视。
3. **密度与删除语义在同一版本改**，学习成本叠加：用户既要重新找按钮，又要重新学「哪些删除能撤」。如果这个版本只能让用户学一件事，应该先学哪个？

**不做会怎样**：用户继续觉得丑、继续多滚。这个痛点是用户自己提的，优先级最高，我不反对做。

**判据**：S1 落地时用真数据跑一次任务计时——1000 条记录、1280×800、任务「找到某条并删除 / 处理 10 条 Inbox」。新壳比旧壳快才算成立，慢就是失败。这个测试半天能做完，比任何设计评审都硬。

### 靶子 6：被排除的那些决定

- **国际化推 0.8**：**同意**，但有一个值得改的小地方。0.7 会新增大量文案（空态、批量条、状态、快照提示、素材页）。如果新文案继续散落在各组件里，0.8 的工作量 = 现有存量 + 0.7 新增。存量口径先说清：按中文字面量算是 **660–742 条**（含 `packages/*` 约 742，只算 `myz-annotator/src` 约 660）；按「含中文的行」算是 **1050 行 / 175 个文件**。建议只加一条约定：**新文案集中到每页一个常量文件**，不引 i18n 库、不改现有代码。成本接近零，0.8 抽取时少扫一半。
- **附件不同步**：**不同意作为默认**，见靶子 4。这是 0.7 最说不清的坑——它把一个数据一致性问题伪装成一个显示问题（「图片在本机」）。
- **知识化推后**：同意，没有异议。只记一句：它是唯一能回答「为什么用 myz 而不是浏览器书签」的东西；0.7 交付后，差异化仍然只有「划线好用」。这不是要它进 0.7，是提醒下一个版本的选题已经有了。
- **多端推后**：同意。

## 三、如果只准砍一项，砍哪个

**砍整页快照（S4）**。

理由按重要性排：
1. 它独占 4–6 周，是唯一会让 0.7 变成两个月的单项。
2. 它是本版唯一的新存储子系统，还要额外养一套上限、LRU 淘汰和失败提示；而淘汰本身和「存档」的语义相冲突（见靶子 1 第 1 条）。
3. 它的价值集中在被规则排除的页面类型上（无限滚动），而它服务得好的页面类型（稳定文章）本来就不太需要它。
4. 它引入「页面在、但标不上」的新失败模式，需要额外的解释成本。
5. 它可以用一天的成本证伪：测「打开原页失败率」。

**砍了会失去什么（必须说清）**：
- 原页 404 / 改版 / 需要登录时，用户看不到当时的上下文。这是真实损失，不是伪需求。
- 也失去一个「未来做知识化时的语料基础」——但那是 1.x 的事，现在不该为它付 4–6 周。

**砍了之后补什么（便宜的兜底）**：
- 原页打不开时，记录详情展示「原文 + 采集时间 + 已保存的选中文字」，并明确说「原始页面可能已变化」。
- 加「打开原页失败」计数，作为下一版的选题依据。

如果快照必须留在 0.7，那就得从别处挪出这 4–6 周。两个方向的代价写在下面，选择权不在我：

| 方案 | 得到 | 失去 | 留给下一版的债 |
|---|---|---|---|
| **A 砍快照** | 0.7 几周内发布；设计修订完整覆盖所有页面（壳、列表、设置、素材、阅读器） | 原页 404 / 改版 / 登录墙时看不到当时的上下文；这类用户要等下一版 | 功能缺口。用户能接受「还没做」 |
| **B 留快照、把逐页规格推 0.8** | 快照能力（对原页会消失的那部分用户） | 设计修订只覆盖壳、列表行、按钮与弹窗；设置、素材、阅读器、查看器仍是旧样式，「不一致」只解决一半 | 半截视觉。用户会问「为什么这一页没改」，比「功能还没做」更难解释 |

两种都不免费。我倾向 A，判据只有一条：**A 的债能用一句「下一版」交代，B 的债一句交代不了。**

## 五、给决策者的四个问题

1. **快照是「必须有」还是「最好有」？** 如果是必须有，0.7 的发布时间要按 4–6 周算，其他三块要被压缩。如果是「最好有」，砍掉它，先用失败率数据决定。
2. **如果留，「存档会被 LRU 清掉」这件事怎么对用户说？** 说清楚，它是诚实的缓存；不说，它是隐性违约。这条决定快照在 UI 上到底叫什么名字（「存档」还是「本机缓存」）。
3. **附件到底同不同步？** 如果不同步，就要接受「换设备后记录还在、图不在」这个用户感知。这需要写进发布说明，不能只写在计划里。
4. **删除的承诺是什么？** 「能撤」还是「删了就没了」？如果承诺「能撤」，批量场景必须有可验证的边界表（靶子 2）；如果做不到，就诚实成「确认 + 永久」，别做成半套。
