# Future Plan — 探索结论与暂缓方向

> 本文记录 MyZ 扩展能力探索中**已达成但暂缓**的方向、结论与理由，避免后续重复讨论。
> 当前 P0 为 PDF 阅读与摘录，见 `docs/plan/pdf-support.md`。

## 背景与产品定位

从"高亮收藏器"出发，探索性地讨论过向"个人知识库"演进（保留来源结构、记录互连、复习重现）。经用户视角审视后**主动收敛为克制版**：

> MyZ = 低摩擦采集 + 结构化查看 + 轻量重现的本地高亮工具。

目标用户：个人知识工作者/学习者本人（单用户）。**本地优先**；不依赖云端 AI。此前“全程无 AI”是收敛期约束，现针对 Inbox 提出可选端侧模型的实验方案，见 `docs/plan/inbox-flow.md`。

## 已确认的总原则

- **AI 不作为全局默认依赖**：历史收敛决策排除 AI；Inbox 实验提案允许用户主动启用端侧 embedding/小模型，云端 AI 仍不在提案范围内。
- **标签只是标记**，不应升级为集合，也不作为集合的绑定依据。
- **奥卡姆优先**：不引入用户难以同时维持的新概念；能被"标签 + 筛选视图 + 时间"近似表达的能力，不额外造对象。
- **当前落地阶段**：集合、自动发现聚合、backlinks、复习调度状态机仍暂缓；**独立 Inbox 已实现**（采集处理队列，见 [`docs/plan/inbox-flow.md`](inbox-flow.md) §11）。
- **顺序**：先解决技术确定、需求高频的 PDF（P0），其余方向按需后置。

## 用户视角审视结论（收敛依据）

对"知识库"野心版特性集的批判性评估：

1. **概念超载**：来源页骨架 + 自动集合 + 双向链接 + 隐式信号 + 间隔重现 + 5 种采集，心智模型过重。
2. **自动魔法是信任杀手**：统计聚类必然有噪音；一旦错误，用户停止信任并绕过；"自动生成后治理"的成本常高于手动维护。
3. **隐式信号驱动调度脆弱且不透明**：用户无法预测"为何这条又出现"；且"不做考核"使其实质不是 SRS，只是带权重的重现。
4. **高频价值被稀释**：真实高频动作是"低摩擦采集 → 快速找回 → 适度回顾"；图谱/backlinks/自动主题属于低频整理癖，易让产品变成"管理工具"。
5. **确认直观且有价值**：来源页章节骨架（即"原文目录"）、新媒介采集（PDF）、轻量重现。

## 暂缓方向明细

### 1. 来源页章节骨架（heading structure）
**结论**：有价值、直观，但暂缓；不参与 PDF P0。
**已定设计要点**（若重启）：
- 只认 `h1–h6` 标题层级；无标题页面不分节。
- 采集时顺带提取一次目录（标题文本 + 层级 + 锚点），**存在该页 bookmark 上**，每条 record 记 `sectionId`；页面级存一次，量级几 KB。
- 明确**不存整份 DOM 快照**、**不在渲染时重抓原网页**（慢、脆、破坏离线优先）。
- viewer 由"按 Range 排序平铺"改为"按 `sectionId` 分组 + 可折叠标题"。
- 已知代价：`sectionId` 是采集时快照，网页改版后会漂移。
- 现有历史标注：**手动触发回填**，不自动补全。

### 2. 集合 / 主题（Collections）
**结论**：用户决定**先不做**。
**已定设计要点**（若重启）：
- 与"来源页"正交：来源页=物理出处，集合=跨页面概念归属，是复习的单元。
- 生成方式：**自动发现聚合 + 手动治理**（自动生成后合并/排除/改名），不绑定标签。
- 发现信号（用户接受全部）：链接图、关键词共现、同来源、时间邻近。
- **必须可解释**：每个集合要能回溯聚合依据（共同词/链接/来源）。
- 备选更克制形态：做成"保存的筛选视图"（确定性、天然可解释），而非统计聚类。

### 3. 自动发现引擎（统计聚类）
**结论**：暂缓；用户曾倾向"直接上统计聚类"，但被收敛评估否决。
**风险**（若重启需先解决）：
- 中文分词是硬前置（`jieba`/`segmentit` JS 移植，几 MB；或退化 n-gram，共现噪音大）。
- 全局重算不可持续，需增量/局部策略。
- 冷启动：记录少时无意义，需降级到同来源/时间邻近等确定规则。
- "必须可解释"限制聚类自由度（越松的簇越难解释）。
- 定位：统计聚类为主、规则兜底、证据可回溯。

### 4. 记录间关联 / 双向链接
**结论**：暂缓。
**已定方向**：混合式——自动聚合打底 + 手动 `[[]]` 双向链接与 backlinks 面板覆盖。

### 5. 重现与复习（Resurface / Review）
**结论**：暂缓；接受"轻量重现"，但不做调度状态机。用户期待形式为**间隔重复 + 随机重现**。
**已定设计要点**（若重启）：
- 单元：**集合/主题**（因集合暂缓，实际被阻塞）。
- 进度维度：**记录 × 集合**。
- 卡片形态：**只推送不考核**。
- 调度信号（隐式行为）：是否打开、停留/滚动、加注/编辑。
- 出口：**Dashboard 重现模块**。
- 已识别矛盾：无考核 → 无法自适应，只能是有权重的重现；建议轻量版 = 随机 / 最近未读 / 集合轮播 + 手动"稍后/不再"。

### 6. 检索与组织
**现状**：Dashboard 已有关键词（正文/批注/标签）、网站、标签、日期区间筛选。
**用户痛点**：① 同页内容无法还原页面结构，只能卡片平铺；② 关联内容无法相互匹配/关联。
**相关候选（未定）**：按主题的保存视图、标签治理（重命名/合并/层级）、全量全文索引。

### 7. 采集面扩展
**现状事实**：截图目前是 `cropAndDownloadSelection`，**裁切后直接下载，不落库成 MyZRecord**（`src/content/stores/toolbar-store.ts`）。
**候选及状态**：
- **PDF**：P0 已立项，见 `docs/plan/pdf-support.md`。
- **截图入库**：补齐"只下载不落库"缺口；形态未定。
- **图片 OCR 文本化**：让截图内文字可搜索；未定。
- **视频/音频时间戳**：按时间戳存片段；未定。
- **移动端捕获**：手机上内容进入同一库；未定（依赖多端宿主）。

### 8. Inbox
**历史结论（收敛期）**：不做独立 Inbox；仅保留最近采集等派生视图。理由是 Inbox 没有明确 triage 目的地，容易退化成“最近添加”并积压。

**现状（2026-10）**：Inbox 已实现为现有记录之上的采集处理队列（不是第二套文库）：新采集进入 `pending`，可标记 / 稍后 / 保留入文库 / 归档 / 删除。**首版不做 enrichments**（关键词 / 代表句 / 重复 / 端侧模型已移出，背景见 `docs/research/omni-inbox/inbox-enrichments.md`）。完整状态模型、迁移规则、同步边界与验收见 [`docs/plan/inbox-flow.md`](inbox-flow.md)（§11 实施状态）。

## 未决问题（重启前需先定）
1. 集合以何形态重启：保存的筛选视图，还是统计聚类？
2. 重现的轻量版边界（是否需要"稍后/不再"状态；是否与阅读进度关联）。
3. 章节骨架的落地时机与增量形态。
4. 截图入库的形态与是否含区域 OCR。
5. 各采集面的优先级（PDF 之后先做哪个）。
6. 标签治理/保存视图/全文索引是否有独立价值。
