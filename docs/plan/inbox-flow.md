# Inbox Flow — 采集处理队列（重设计提案）

> 状态：**已审核通过**（第二轮 review 修复见 §10）。正按顶部总顺序实施；进度见文末「实施状态」。
>
> 本版落实三项决定：
> 1. Inbox **默认启用、可关闭**；关闭后新采集直接进入文库（等价现状）。
> 2. 工作流状态作为**独立子流**记录同步（`<accountId>/streams/inbox/`），与主流高亮物理隔离、各自按 recordId 做 latest-write-wins，消除“整条记录互相覆盖”的同步冲突；子流协议与优化见 `docs/plan/e2ee-sync-evolution.md`。
> 3. 本计划**不再包含任何 AI / 自动化 / 基于统计或分词的归类与关联**。相关方案与实验结果已移到 `docs/research/omni-inbox/inbox-enrichments.md`，本版只呈现记录自带的确定性信息。
> 4. **总增量顺序**：安全 quick wins（QW1–QW5）→ 安全密钥模型（设备绑定 D/roster/按设备签名，clean break）→ sync 子流（`e2ee-sync-evolution.md` I2–I6）→ 本文 Inbox 状态与 UI。各计划的“第二轮 review 修复决议”记录具体修正。

## 1. 要解决的问题

MyZ 当前的采集路径已经能把内容快速写入文库，但“刚刚随手保存”和“确认以后要保留”的记录没有区别。用户会遇到三种摩擦：

- 采集时被迫马上决定标签、用途或归属；
- 保存以后难以知道哪些内容还没处理；
- 文库混杂了未读、待判断和已经确认有价值的记录。

Inbox 的职责是提供一个**可清空、可恢复、可批量处理的采集队列**，而不是再做一个文库副本。

### 1.1 文库与 Inbox 的边界

| 区域 | 职责 |
| --- | --- |
| Inbox | 新采集内容的处理队列，默认只展示待处理内容 |
| 文库 | 已确认保留的长期记录，仍是记录的主要浏览、编辑、搜索入口 |
| 归档 | 已处理但不进入文库默认列表的记录，仍可通过文库的“归档”筛选找回 |
| 删除 | 用户明确放弃的记录，沿用现有删除与同步删除语义 |

Inbox 不替代文库。保留后的记录仍由文库负责完整查看、编辑、来源定位、导出和搜索。

### 1.2 采集入口规则

- Inbox **默认启用**，但用户可以在设置中关闭（见 §3.5）。
  - 启用时：网页、PDF、EPUB 的新采集默认 `pending`，包括书签型记录；没有正文的记录仍可由用户保留、归档或删除。
  - 关闭时：新采集直接 `kept`，不产生待处理记录，行为与现状一致。
- 采集条同时提供“直接入文库”快捷动作，写 `kept`，不进入待处理队列。
- 导入默认不产生待处理记录（等同 `kept`）；导入流程可显式选择“导入到 Inbox”写入 `pending`。
- 队列数量和最早积压时间必须可见，避免待处理列表变成无提示的永久 backlog。

## 2. 已经审察过的结论

### 2.1 旧 Inbox 的缺陷

- 旧 Inbox 的时间视图等价于“最近添加”。
- 旧 Inbox 的页面视图重复了文库已有的来源分组。
- 没有聚类结果时，旧主题视图只能显示“尚未启用”，不能证明 Inbox 有独立价值。
- 当前 UI 没有处理状态，因此不能表达“待处理”和“已完成”的差异。

### 2.2 同步冲突（本版的核心修正）

现有同步是**按 recordId 整条 latest-write-wins**：

- 每条记录 `recordId = h:<id>`，整条 `MyZRecord` 作为 payload 上传，远端应用时整条覆盖写回（`myz-annotator/src/background/sync/records.ts`）。
- 合并规则：同 recordId 取 `updatedAt` 最大者，相等时比 recordHash；**没有字段级合并**；删除是“最新 manifest 中缺席”的硬删（`packages/sync-core/src/E2EE_SYNC_SPEC.md`）。
- 因此只要把 `inbox.status` 挂在同一条 `MyZRecord` 上，任何一次“标记 / 保留 / 归档 / 稍后”都会 bump 该记录的 `updatedAt` 并整条重传；此时另一端对同一记录的正文、批注或标签编辑会被整条覆盖（反之亦然）。“先读最新再写”只能缩小在线窗口，离线跨设备仍会丢。

结论：**状态必须与正文物理隔离并独立同步**，放进独立子流（`<accountId>/streams/inbox/`）。这样状态写入只动子流记录，正文编辑只动主流记录，二者互不覆盖；子流的协议契约与同步优化见 `docs/plan/e2ee-sync-evolution.md`。

### 2.3 自动语义能力的边界

首版**不依赖 embedding、聚类、生成模型，也不做基于统计或分词的自动归类与关联**。连此前设想的“关键词 / 代表句 / 统计去重 / 语言检测”等确定性 enrichments 也一并移出本计划，只保留记录自带的确定性信息（采集时间、来源、页码/章节、精确重复等，见 §5）。原因：Inbox 的定位是“用户自行管理”，不替用户做判断；去掉这些管线后，实现范围显著收缩，也不再需要本地索引与算法版本管理。被移出的完整方案与实验结果见 `docs/research/omni-inbox/inbox-enrichments.md`。

## 3. 状态模型

### 3.1 状态与存储

Inbox 状态是记录的用户工作流元数据，但它**既不写入 `MyZRecord`，也不进入主流 manifest**，而是作为**独立子流**中的记录（子流协议见 `docs/plan/e2ee-sync-evolution.md`）：

```ts
type InboxStatus = "pending" | "snoozed" | "kept" | "archived"

type InboxStatusState = {
  targetId: string          // 对应的正文记录 id
  status: InboxStatus
  snoozedUntil?: string
  handledAt?: string
  changedAt: string
}

type InboxMarkState = { targetId: string; marked: boolean; changedAt: string }
type InboxRelationState = { targetId: string; relatedIds: string[]; changedAt: string }
```

- 状态位于子流 `<accountId>/streams/inbox/`，与主流（`h:` 高亮）物理隔离。
- **本地持久化**：三层状态存独立 IndexedDB store（如 `inbox_state`），由子流 collect/apply 读写；Inbox 启用后本地即时生效，未配对前仅本地、不跨设备。
- 每个独立可变字段拆成独立 recordId（`status:<targetId>` / `mark:<targetId>`），各自 LWW，跨字段并发不互相覆盖。
- **关联用逐边记录 `rel:<src>:<dst>`**（存在即关联，删除即解除），避免 `relatedIds` 数组整条 LWW 丢并发关联。
- 正文记录保持 `h:<id>` 与 `MyZRecordV1` 不变，不新增 `inbox` 字段。
- **状态动作（保留/归档/稍后/标记）一律写显式记录，包括 `kept`**，因此 `handledAt` 存在，回顾统计与 5 秒撤销才能工作。
- **缺省规则：没有 `status:` 记录 = `kept`，仅表示“从未处理”**（历史记录、Inbox 关闭时的采集）；不承担“已处理但无记录”的语义。
- Inbox 启用时，新采集写 `pending` 记录；关闭时不写，视为从未处理。
- 字段语义：
  - `pending`：新采集，等待处理；Inbox 默认队列只展示此状态。
  - `snoozed`：稍后处理；到 `snoozedUntil` 后重新进入待处理列表。
  - `kept`：保留入文库；退出 Inbox，出现在文库常规视图。
  - `archived`：归档；退出 Inbox，仍保留在文库，默认文库列表隐藏，可通过归档筛选找回。
  - `marked`：用户标记需要注意；独立标记，不改变队列状态。
  - `relatedIds`：用户手动建立记录间关联；属于工作流元数据，放在独立的 `rel:` 记录，避免与正文编辑及状态变更冲突。
  - 删除不作为普通状态：沿用现有删除流程，首版执行前确认，不承诺撤销。现有删除会写入同步删除记录并删除本地记录；真正的回收站需要单独设计。

### 3.2 迁移规则

- 历史记录没有 `status:` 状态记录时视为 `kept`（从未处理），不产生待处理内容。
- Inbox 启用后，新的网页、PDF、EPUB 采集写入 `pending`；采集入口的“直接入文库”写 `status=kept`（含 `handledAt`）。
- 导入默认视为 `kept`（从未处理）；导入 UI 可显式“导入到 Inbox”写 `pending`。
- 采用 clean break（无向前兼容）：所有端升级到新账号/格式版本；总顺序见顶部与 `docs/plan/e2ee-sync-evolution.md`。

### 3.3 状态迁移

```text
new capture ──> pending ──> kept ──> Library（写 status=kept，含 handledAt）
                    │
                    ├──────> archived ──> Library / 归档筛选
                    │
                    └──────> snoozed ──> 到期后 pending
                    │
                    └──────> deleted ──> existing deletion flow

无 status 记录（历史 / Inbox 关闭时采集）=== kept（从未处理）
mark: / 逐边 rel: 记录与 status 独立，可作用于任意状态
```

所有动作都应可批量执行；保留、归档、稍后处理和删除都需要即时反馈。状态变化只改变工作流归属，不修改正文、来源和定位信息。

### 3.4 同步与冲突（子流）

- **物理隔离**：Inbox 状态走独立子流 `<accountId>/streams/inbox/`，使用独立 master key `C_inbox = HKDF(D, "stream:inbox:master")`（D 为设备绑定后的数据密钥，见 `e2ee-security-hardening.md`）、独立版本指针、独立锁与 GC；主流（高亮）格式与密钥模型同样按 clean break 迁移。
- **独立时钟**：`status:` / `mark:` / `rel:` 记录各有独立 `recordId` 与 `updatedAt`，与正文记录、以及彼此之间都各自 LWW，互不覆盖。
- **前向兼容**：子流 v1 自带显式墓碑、opaque preservation（未知记录原样保留）、`<=` 版本解析与 `minReaderVersion`、`streamVersion` 单调抗回滚；日后在子流内新增类型不会被早期子流客户端删除。
- **删除**：删除正文记录时写入对应状态记录的墓碑；压实与孤儿清理由子流 GC 负责。
- **标签与正文编辑**仍发生在正文记录上，沿用现有整条 LWW（与今天一致，不是新引入的回归）。Inbox 里的打标签/改正文动作仍可能与其他端的正文编辑竞争；首版接受这一点，只有状态相关元数据（status / mark / rel）走子流。
- **设置不同步**：“是否启用 Inbox”属于本地设置，按设备生效；一个设备关闭 Inbox 时不会为采集写 `pending`，但其他设备写入的状态记录仍会同步过来。
- **依赖**：本节依赖 `docs/plan/e2ee-sync-evolution.md` 的 I2–I6；在该计划落地前，Inbox 状态只能本地生效，不能跨设备同步。

### 3.5 启用与关闭

- 默认 `inbox.enabled = true`（新安装与升级都默认开启，但升级不迁移历史）。
- 关闭 Inbox：采集不再写 `pending`；已存在的 `pending` / `snoozed` 记录保留，重新启用后继续显示。
- **关闭 Inbox 后，其他设备同步来的 `pending` 记录仍须在文库以“待处理”筛选/徽标可见**，不得两个视图都不可见。
- 关闭时提供一次确认，说明“新采集将直接进入文库，不再进入待处理队列”。

## 4. Inbox 页面重新设计

### 4.1 页面结构

Inbox 不再以“时间 / 主题 / 页面”作为顶层三视图，而是：

```text
Inbox
├── 左侧栏（状态导航 + 标签，可拖拽投放）
│   ├── 待处理（默认）/ 稍后处理 / 已标记
│   └── 标签列表（点击筛选；把记录拖到标签即打标签）
└── 主队列（单栏）
```

左侧栏与顶部包含：

- 左栏：队列状态导航与标签列表；标签是拖拽投放目标，复用正文记录上的标签（不新增分类模型）；点击标签筛选队列，窄屏收进抽屉；
- 待处理数量、最早积压时间、最近进出比（健康度提示）；
- 搜索框，搜索原文、批注、标题、标签与来源；
- 来源类型、日期、语言（按记录自带字段）等筛选；
- 批量选择和批量动作；
- “专注处理”入口与“返回文库”。

首版不做独立“处理记录”页面，只在动作完成后提供短时反馈；完整历史仍在文库。

### 4.2 默认列表

列表按采集时间倒序，新的内容优先处理。每一行包含：

- 选择框；
- 类型和状态标识；
- 原文摘录的 2–4 行预览；
- 来源标题、域名、页码/章节和采集时间；
- 可能完全重复（精确内容 hash）与同来源已有记录的提示；
- 行内动作：标记、保留、稍后、归档、删除。

列表行不嵌套多个不可预测的交互。常用动作直接可见，更多信息在右侧详情面板或移动端底部抽屉中打开。

### 4.3 专注处理模式（Quick Triage）

这是提升日常效率的主交互，一次处理一条，尽量不用鼠标：

- 卡片式一屏一条，显示原文预览、来源与采集时间；
- 进度 `n / total`，动作后自动进入下一条；
- 单键动作：`K` 保留、`A` 归档、`S` 稍后、`D` 删除、`M` 标记、`T` 标签、`L` 关联、`Space` 下一条；
- 保留/归档/稍后/标记提供 5 秒撤销；**删除为破坏性动作，仅确认、不提供撤销**（首版无回收站）。
- 默认动作为安全动作（保留），危险动作（删除）需要确认；
- 引用 GTD 的两分钟规则：能立刻判断的就当场判断，避免整队拖延。

### 4.4 手动归类、标签与关联

不替用户做决定，但要把“决定”的成本降到最低：

- 标签输入从**用户已有的标签**自动补全，按“最近使用 / 本来源用过 / 全部”分组；不做 AI 推荐。
- 左侧栏标签列表可作拖拽投放目标：把队列记录拖到某个标签即给它打上该标签（复用正文记录标签，不新增分类模型）；点击标签筛选队列。
- 数字键快选常用标签（Zotero 式），`Shift+Enter` 批量加多个标签。
- 保留、归档、稍后、删除支持多选批处理；“稍后”提供固定分桶（今天晚些 / 明天 / 本周 / 某天）。
- “标签后归档”（Tag and Release）：先打最小标签再归档，记录可被搜索找到但离开队列。
- 手动关联：用逐边记录 `rel:<src>:<dst>` 显式关联两条记录（存在即关联）；不自动推断，避免数组 LWW 丢并发。
- 采用“先捕获、后定型”的思路：采集端保持零决定，标签、关联、归类都在 Inbox 处理阶段完成。

### 4.5 移动端 / 窄屏

列表改为单列，动作进入底部操作区；详情使用抽屉；专注处理模式全屏、单键动作映射为底部按钮；支持滑动手势（保留 / 归档 / 稍后 / 删除）并保留撤销。

### 4.6 回顾

首版只做两类**确定性、非算法**的回顾：

- **Inbox 清理提醒**：在 Inbox 与扩展角标显示待处理数量与最早积压时间（角标最多显示 1，避免数字焦虑）；可选每日提醒，默认开启、可关闭（chrome.alarms）。
- **每周回顾**：一个轻量检查面，列出超期的 `snoozed`、最老的 `pending`、本周新采集与已处理数量；提醒用户清空队列并复核归档。可沿用 GTD 每周回顾的“清空收集箱”思路，但只覆盖 Inbox 范围。

明确：首版**不做**间隔重复 / 主动回忆 / 知识重放（那是面向已保留高亮的独立功能，需要单独的复习模型，见 §9）。

## 5. 记录自带的确定性信息

Inbox 只呈现记录自身或确定性计算得出的信息，不做模型或统计推断：

- 采集时间、`createdAt` / `updatedAt`；
- 来源类型（网页 / PDF / EPUB）、标题、域名；
- PDF 页码、EPUB 章节等定位信息；
- 内容长度分档（短摘录 / 长摘录 / 空内容）；
- 完全重复检测：对规范化文本做 hash，仅提示“完全重复”，不做模糊相似度；
- 同来源已有记录数量（同 URL / 同 PDF 页 / 同 EPUB 章节）。

这些都不改变 `inbox.status`，也不写入用户标签。

## 6. 派生数据与隐私边界

- Inbox 状态属于同步数据，走独立子流上传（加密后存储），是跨设备一致的状态来源；主流高亮记录不受影响。
- 状态记录只承载工作流元数据（status / mark / rel 与时间戳），不复制正文。
- 首版不建立任何本地 enrichment 索引，因而也没有索引失效、算法版本或不同设备结果不一致的问题。
- 删除正文记录时写入对应状态记录的墓碑；重建索引等概念在首版不存在。

## 7. 实现增量（审核通过后执行）

1. **前置**：按顶部总顺序先完成 (a) 安全 QW1–QW5；(b) 安全密钥模型 KM1–KM4 + clean break（D/roster/按设备签名）；(c) `e2ee-sync-evolution.md` 的子流 I1–I6。Inbox 跨设备状态在 (c) 前仅本地生效，本地 UI 可先行。
2. **状态模型**：新增 `InboxStatusState` / `InboxMarkState` / `InboxRelationState` 类型与存储；实现缺省 `kept`、`pending` 写入；Inbox 启用/关闭设置（默认启用）。
3. **队列动作**：待处理 / 稍后 / 已标记列表，标记、保留、归档、稍后、删除确认与批量动作；文库增加归档筛选但保持原有入口。
4. **专注处理模式**：单条卡片流、键盘单键动作、自动下一条、5 秒撤销、进度。
5. **手动归类体验**：已有标签自动补全、数字键快选、批量打标签、稍后分桶、手动关联（`rel:` 记录）。
6. **回顾**：Inbox 健康度提示 + 每日提醒 + 每周回顾检查面。
7. **移动端 / 窄屏**：单列列表、底部动作、抽屉详情、滑动手势。
8. **同步与冲突验证**：状态记录与正文记录、以及 status/mark/rel 彼此互不覆盖；墓碑与孤儿清理；跨设备最后动作。

## 8. 验收标准

- Inbox 默认启用；新采集在保存后立即进入 Inbox，不等待任何后台处理。
- 历史文库记录不会进入待处理队列（无状态记录即 `kept`）。
- 关闭 Inbox 后新采集直接进入文库常规视图。
- 状态动作与正文编辑在不同设备并发时**互不覆盖**：状态记录与正文记录各自 LWW，均有单元测试与双端模拟测试覆盖。
- 保留后记录进入文库常规视图；归档后记录仍可通过归档筛选找回，且仍能被明确的全量搜索和导出包含，不得造成数据消失。
- 保留、归档、稍后处理、标记、删除均可批量执行，并有数量确认与完成反馈；删除首版需要确认，不承诺撤销。
- 专注处理模式的单键动作、自动下一条与 5 秒撤销在 Playwright 中覆盖。
- 不自动创建标签、不自动归类、不自动关联、不自动保留或归档。
- Inbox 不复制文库编辑器，不替代文库查看、搜索、导出和来源定位。

## 9. 待审核决定

- 状态是否采用“缺省 `kept` + 仅必要的 `status:` 记录”模型；本提案推荐是。这使历史迁移为零成本，代价是 `pending` 采集多写一条状态记录。
- 状态走独立子流而非主流；协议细节以 `docs/plan/e2ee-sync-evolution.md` 为准；本提案推荐是。
- 标签与关联的归属：标签继续放正文记录（沿用现有 LWW），状态相关元数据放子流；本提案推荐是，并接受标签编辑仍可能与正文编辑竞争。
- `marked` / `relatedIds` 是否进入首版：本提案推荐进入，且各用独立 recordId；`relatedIds` 只做手动关联，不做推断。
- 每日提醒的默认状态：默认开启、可关闭；本提案推荐是。
- 间隔重复 / 知识重放是否立项：本提案决定首版不做，作为独立功能另行评估。
